# Troubleshooting

Run `xj doctor` first: it says what works, what does not, and why. If that is not enough, reproduce the problem with `xj --debug`; the raw requests and responses sent to the API are saved under `debug/` in the session log (keys masked). When reporting a problem, paste the output of `xj doctor --report` (it contains no keys and no conversation).

| Problem | What to do |
|---|---|
| The sandbox cannot start | Install what `xj doctor` says is missing (macOS: ripgrep; Linux: bubblewrap, socat, ripgrep, sandbox-runtime). Until then every command is refused; if you really need to run commands without the sandbox, start with `--no-sandbox` (every command asks) |
| Linux: apply-seccomp not found, or the wrong version | Reinstall sandbox-runtime with the line in the message (`npm install -g --ignore-scripts @anthropic-ai/sandbox-runtime@<version>`, see "The Linux sandbox" in [install.md](install.md)). With nvm, install it with the Node version that runs xj |
| 401, 403 | The key is wrong or lacks permission. `xj doctor` says where the key is read from |
| 429 | Rate limited. Xing Janus backs off according to retry-after, retrying up to 3 times |
| Quota used up | Check usage and budget in the provider's dashboard |
| Context too long | It summarizes automatically and tries again; if it is still too long, start a new conversation with `/clear` |
| Ollama says the context is too small | Restart Ollama with `OLLAMA_CONTEXT_LENGTH=32768` |
| A notice that reasoning blocks were dropped, or a history check returning 400 | That is a Xing Janus bug: reproduce it with `--debug` and report it |
| The terminal is broken (the scroll region was not restored) | Type `reset` or `printf '\e[r'` |
| At startup: "xj: ignoring these NODE_OPTIONS: …" | `--import`, `--require` and the like in `NODE_OPTIONS` would run other code inside xj (outside the sandbox, with access to the keys), so xj only accepts `--use-system-ca`, `--use-openssl-ca` and `--max-old-space-size` and drops the rest. If you set it yourself you can ignore this; if not, find out who set it (for example the project's `.envrc`) |

## docker commands fail in the sandbox

`Cannot connect to the Docker daemon`, `permission denied ... docker.sock`: the sandbox blocks the connection to Docker (whoever can tell Docker what to do can reach the whole computer).
To use it, list `docker` in `sandbox.excludedCommands` in the config (it asks every time and only runs outside the sandbox after you say yes; see "Docker" in config.md),
or use skip-all-permissions mode in a container or VM you can throw away.

## Using WSL, but giving Windows paths

`C:\\Users\\...` is not a path inside WSL; use `/mnt/c/Users/...`. But **keeping the project there is not recommended either**:
crossing file systems is slow, and hard links and inodes behave differently (the secret-file checks rely on inodes, so you lose a layer of protection).
Keep the project on WSL's own file system (for example `~/code/project`); `xj doctor` checks this for you.

## Windows

The native version (the sandbox is alpha).

| Problem | What to do |
|---|---|
| "The Windows sandbox is not installed: every command asks" | That is the normal state before the sandbox is installed (it needs administrator rights). To install it, use PowerShell opened with "Run as administrator" and install sandbox-runtime for the whole computer (`%ProgramFiles%\sandbox-runtime`) as in "Windows" in [install.md](install.md), then run `windows-install` once. Restart xj afterwards |
| "srt-win.exe is installed in a user folder (the srt-sandbox account cannot open it…)" | Installed with a normal-rights `npm install -g` following older steps, it ends up in `%APPDATA%\npm` under your account: the sandbox account cannot read there, so the sandbox cannot start. Reinstall it for the whole computer as in the row above (meanwhile every command asks; nothing runs without asking) |
| "commands in the sandbox can write to the srt-win.exe folder" | sandbox-runtime is installed where normal users can change it (for example `C:\tools`, or a folder you created on another drive): commands in the sandbox could replace the sandbox itself, so xj does not use it (every command asks). Install it under Program Files as two rows above |
| The sandbox is installed, but xj says it cannot start | Every command is refused then (the same as on macOS and Linux). Follow the message from `xj doctor`; common causes are firewall rules that were cleared (run `windows-install` again) and a working folder on a network drive (the sandbox account cannot see your mapped drives; keep the project on a local disk) |
| Tools such as node or python are not found in the sandbox | The sandbox runs as another account (`srt-sandbox`) that cannot read tools installed under your account. **At start-up, if something on your PATH cannot be read inside the sandbox, xj says which tool it is, where it is installed, and how to open it** (added 2026-10-27; when a command actually fails because of this, the model is also told "it is installed, the sandbox just cannot read it", so it does not ask you to install software you already have). xj opens common locations by project type: always Node's install folder, per-user Git, Scoop, and what winget installs under your account (`WinGet\Packages`, `Links`); for Node projects (with a `package.json`) also npm's global installs; for Python projects per-user Python; **when the folder is not recognizable as any project type yet (a brand-new empty folder, e.g. "start me a Python project") Python and Node are opened anyway**; for Android projects (with Gradle files such as `build.gradle`) the Android SDK and `~/.gradle`. Flutter projects do not get Flutter/fvm or the Pub cache (flutter and dart always run outside the sandbox; see "Tools that cannot run in the sandbox" in config.md). Install anything else for the whole computer (Program Files; for winget see the next row), or add it to `sandbox.toolchainReadable` in the config (if you write that field yourself, xj opens exactly what you wrote and adds nothing) |
| A tool that winget installed for the whole computer (jq and the like) is not found in the sandbox, or gives Permission denied when called by path | Portable tools installed by `winget install` as administrator (without `--scope user`) live under `Program Files\WinGet`. Everyone can read those folders, but the executables themselves can only be run by the installing account and administrators (winget downloads them to your temp folder and then moves them, and the permissions move along), so the sandbox account cannot run them. **xj says which tool it is and its winget package ID** (at start-up and when a command actually fails because of it, in Git Bash and in localized PowerShell; the model is also told not to say "not installed"). To use it inside the sandbox, reinstall it with `winget install --scope user --id <package ID>` (installed under your account, which xj opens to the sandbox) and restart xj, or add the command to `sandbox.excludedCommands` in the config (runs outside the sandbox, asks every time). Adding it to `toolchainReadable` does not help: the file's own permissions are what block the sandbox |
| Gradle in the sandbox says a folder under `~/.gradle` cannot be created (Access is denied) | The Windows sandbox only opens existing folders under `~/.gradle` for writing, and `wrapper` and `init.d` read-only (opening all of it would mean blocking the wrapper and init scripts that run outside the sandbox separately, adding over ten seconds at start and at exit). Create new folders by running Gradle once outside the sandbox (for example `flutter build apk`); or list them yourself in `sandbox.writable` in the config (for example `["~/.gradle", "C:\\Users\\<you>\\AppData\\Local\\Pub\\Cache"]`: if you write that field, xj opens it as written, as a whole, which is slower) |
| git in the sandbox says `detected dubious ownership` | The Windows sandbox runs as another account, so your repos are "owned by someone else" to it, and git only works in them when they are listed in safe.directory. xj lists them itself: the project, nested repos (submodules and the like) **that exist when the sandbox starts**, the writable folders, the toolchains, and the `safe.directory` entries from your own `~/.gitconfig` (except a bare `*`). **Repos you opened for reading with `/add-dir` or `extraReadable` are not listed, on purpose**: git runs commands from that repo's `.git/config`, and `git status` is on the whitelist and runs without asking. A nested repo created during the session (for example `git clone` inside the project) works with Git 2.46 or later; with an older Git, restart xj or update Git |
| xj with the sandbox takes a long time to start (Android projects; not Flutter projects) | Flutter projects no longer open the Flutter SDK, Pub cache, Android SDK or `~/.gradle` to the sandbox (flutter and dart always run outside it; on that machine a Flutter project went from 42–77 seconds to 5–13 seconds). What follows describes the earlier behaviour, which still applies to Android projects: Opening a folder to the Windows sandbox means changing the permissions of every file under it: the Flutter SDK, Pub cache, Android SDK and `~/.gradle` often add up to hundreds of thousands of files (tested 2026-10-27: over 300,000 files, 45–55 seconds to start on that machine, longer for the first start after booting; quitting does not wait, the permissions are taken back in the background). The screen says what it is waiting for, and every 10 seconds which folder it is on. To make it faster, set `"sandbox": { "excludedCommands": ["flutter", "dart"], "toolchainReadable": [], "writable": [] }` in the config: flutter and dart then run outside the sandbox and ask you every time, and other commands stay in the sandbox |
| The sandbox is on but the whitelist does not apply and every command asks, saying something is "writable outside the sandbox" | When the sandbox starts, xj actually tries to write to every folder on your PATH (also the toolchains the sandbox can read, Git Bash's own folders, and the SDKs of `excludedCommands`): if one is writable, commands in the sandbox can put a program there that later runs outside the sandbox with your permissions, so the whitelist stops applying (added 2026-10-27). The usual cause is tools installed somewhere any logged-in account can change, such as `C:\tools` or `D:\`. **A PATH entry pointing to a folder that does not exist counts too** (e.g. the software was uninstalled but the PATH entry stayed): the sandbox only has to create it in the parent folder and put a program in it. The simplest fix is to remove it from PATH; when the parent is a drive root, the printed icacls only blocks creating files and folders in that root itself (`(WD,AD)`, not inherited). To get the whitelist back: reinstall those tools under `Program Files`, or run the `icacls "<folder>" /deny *<SID>:(OI)(CI)(WD,AD,WEA,WA,DC,DE)` printed in the warning as administrator (it names the highest folder that is writable all the way up, such as `C:\src`), then restart xj. xj asks whether to block it for you (as administrator, with a UAC prompt; you can allow it permanently), and skip-all-permissions mode blocks it without asking; see "Skip-all-permissions mode" in usage.md |
| With the sandbox on, `flutter` and `dart` ask "run outside the sandbox" every time | Expected: they cannot run in the sandbox (they write the SDK's `bin\cache` on every run, and hang in the sandbox). xj tells the model so, and it asks to run that one command outside the sandbox, asking you every time. To avoid this, start with `xj --no-sandbox` (no sandbox at all), or set `"sandbox": { "excludedCommands": ["flutter", "dart"] }` (also asks every time). See "Tools that cannot run in the sandbox" in config.md |
| `CRYPT_E_REVOCATION_OFFLINE` from `curl` or `git` over https in the sandbox | Windows' built-in TLS (schannel) cannot reach the certificate revocation check (the sandbox's firewall blocks it). Use `curl --ssl-no-revoke` or `git -c http.schannelCheckRevoke=false` |
| Git Bash not found | Install Git for Windows, or write `"windows": { "gitBash": "C:\\…\\bin\\bash.exe" }` in the config. `C:\Windows\System32\bash.exe` is WSL's launcher, not Git Bash, and xj never uses it |
| node scripts in the sandbox (`npm test`, `node --test`, `node file.js`) fail with `EPERM: operation not permitted, lstat 'C:\Users\<you>\Desktop'` | Node reads the attributes of every parent folder when resolving a script's real path. xj gives those few levels in your home folder a "read attributes" permission when it starts the sandbox (see "Differences" below), so this normally does not happen. If it still does, check for the startup notice that the parent folders could not get the permission (for example a work computer that blocks PowerShell): then run such commands outside the sandbox (add `npm` and `node` to `sandbox.excludedCommands` in the config; they ask you every time) |
| PowerShell in the sandbox prints paths like `Project:\src\…` | The sandbox account cannot read the parent folders of your home folder, so PowerShell cannot enter the working folder by itself (it stays in `C:\`); xj therefore opens a `Project:` drive pointing at the working folder. `Project:\src\a.ts` is `src\a.ts` in the project |
| Every PowerShell command (other than ones like `Get-Content`) asks | The PowerShell whitelist only accepts very simple forms: read-only cmdlets (`Get-ChildItem`, `Get-Content`, `Select-String`, `Select-Object`…) with plain words or single-quoted values as parameters, and no `$`, parentheses, double quotes or `>`. The question says what did not qualify (for example "it has $ (variables, subexpressions)"). For other commands, let it use bash (Git Bash) |
| Pressing Ctrl-C during `xj -p` in cmd: after xj quits, cmd asks "Terminate batch job (Y/N)?" | cmd.exe asks that itself (xj.cmd is a batch file); answering Y or N makes no difference. Ctrl-C in a conversation (without `-p`) is a key xj handles itself, so it does not happen there, nor when running `xj -p` from PowerShell |
| An MCP server says "The Windows sandbox cannot run the MCP server …" | The Windows sandbox cannot connect stdin to programs in the sandbox yet, and MCP (stdio) relies on stdin. To use the server, set its `sandbox` to `false` in the config: it then runs outside the sandbox with your permissions, and every call still asks you (unless listed in `autoApprove`). Only do that for servers you trust |
| Worried that typing `xj` in someone else's repo runs a same-named program from the repo | When xj.cmd looks for node it skips the current folder and anything under the working folder (a PATH entry that reaches into the working folder through a junction is not recognized: a batch file cannot get real paths, though the sh launcher Git Bash uses can). But finding xj.cmd itself is cmd.exe's job: cmd looks in the current folder first, so an `xj.cmd` placed in the repo would run. Prefer PowerShell (it does not look in the current folder), or set the system environment variable `NoDefaultCurrentDirectoryInExePath=1` |
| At startup: "xj: NODE_OPTIONS is ignored …" | The Windows xj.cmd ignores NODE_OPTIONS completely (a batch file cannot split quotes, so it cannot keep just the safe options); `--use-system-ca` and `--use-openssl-ca` in it are passed to node directly |
| Garbled output (non-ASCII text) | xj already switches PowerShell tool output and file reads and writes with `Get-Content`/`Set-Content`/`Out-File`/`>` to UTF-8 (Windows' built-in PowerShell 5.1 writes a BOM, so let it create and change files with the write and edit tools). Windows' built-in programs run from Git Bash (`ipconfig`, `cmd //c dir`) use the console code page, which xj cannot change |
| The "Process cleanup" row of xj doctor says job objects are unavailable | xj uses Windows' built-in PowerShell 5.1 in the background to manage job objects (stopping every process a command started on Ctrl-C or timeout). If a work computer blocks PowerShell or Add-Type, that is unavailable: Ctrl-C may then not stop every background process Git Bash started, and the watchdog tries again when xj quits |
| Programs a command starts (windowed programs, ones started with `start`, the Gradle daemon) disappear as soon as the command ends | xj puts every program a command starts into the same job object and stops it as a whole when the command ends (that is the only way to clean up background processes Git Bash starts; with the sandbox on, the sandbox's own job object does the same), which is stricter than macOS and Linux. Start programs you want to keep (dev servers, emulators, editors) yourself, outside xj. Gradle starts a new daemon for each build (a few seconds longer each time; the result is the same) |
| Commands in Git Bash cannot find `~/.gitconfig` or `~/.ssh` (domain accounts, a home folder on a network drive) | Without the sandbox, xj runs Git's `usr\bin\bash.exe` directly, and when HOME is not set it fills it in the way Git Bash does: `HOMEDRIVE` + `HOMEPATH` if that folder exists, otherwise `USERPROFILE`. To always use a particular folder, set `HOME` in your Windows user environment variables |

**Differences of the Windows sandbox from macOS and Linux** (alpha):

- Secret files are written into the permissions (ACLs) one by one when the sandbox starts. Secret files that appear later are blocked separately before each command runs.
  In a very large project (more than about twenty thousand files, not counting node_modules and the like) the scan cannot finish, and secret files it did not find are not blocked by the sandbox: the whitelist then does not apply and every command asks; the startup lines and `xj doctor` say so.
- For protected files that do not exist yet (for example `.vscode/tasks.json`, new files under `.git/hooks/`), the sandbox cannot block their creation:
  xj's tools and redirections still block it, and if a command creates one, the result tells you to check it.
- After `/add-dir`, the sandbox has to restart (that is the only way Windows permissions can change), and running MCP servers restart too.
- When the working folder (or an opened toolchain, such as npm's global installs) is under your home folder, each folder level above it (for example `Desktop`, `AppData`) gets one extra permission while the sandbox is on:
  "`srt-sandbox`: read attributes only" (without it, node scripts in the sandbox fail with EPERM). All the sandbox can see of those levels is the folders' own attributes, such as timestamps and hidden;
  it cannot list their contents or read files. xj removes the permission in the background when it quits; with several xj running, the last one to quit removes it; if xj is force-quit, the next sandbox start cleans it up.
- All xj sandboxes use the same `srt-sandbox` account: with two xj running at once, folders opened for one of them (the project, toolchains)
  are readable from the other's sandbox too, until the first quits and its permissions are taken back. Do not have a trusted project open while running xj in an untrusted one.
- When the sandbox starts, it sets permissions on the whole project and the opened toolchains: with many files (node_modules, Flutter/Android toolchains) this takes a while, and the screen says what it is waiting for.
  At exit the permissions are handed to a background program to take back, so xj does not wait; until it finishes, the sandbox account keeps those permissions (over half a minute for large toolchains).
- If that background program is interrupted (for example by logging out or shutting down before it finishes), the sandbox account keeps the toolchain folders' permissions for a while,
  until the next time the sandbox is used on this computer (srt-win also cleans up after xj sessions that have ended).
- When the project is on a separate drive such as D: that is open to all users, the sandbox account can also read and change other folders on that drive (see cerberus.md).
  Keep projects under your home folder (`C:\Users\<you>\…`): by default only you can read there.
- Commands in the sandbox get the sandbox account's own environment: xj writes the few variables it sets itself (no password prompts, the npm cache, the sandbox's git config) and `env.passthrough` from the config
  in front of the command, so they appear on srt-win's command line, together with the sandbox proxy's credentials (generated by the library, new on every start).
  Every program running as the same account can see command lines: **do not put keys in `env.passthrough`**.
- PowerShell commands outside the whitelist that mention protected files (`.git/hooks`, `.vscode`…) are always blocked: xj cannot tell whether they read or write. A whitelisted read such as `Get-Content .vscode\tasks.json`
  runs as usual; it can also use read to see the contents.
